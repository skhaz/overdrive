# Agents

## Rules for this file

- Technical details live here. `README.md` is for users: plain words, no internals.
- Write simple, direct English. Only what matters. No filler.

## Commits

Commit each change when it is complete. Do not ask before you commit.

Always run `swift test` before every commit. Commit only when all tests pass. GitHub Actions does not run the tests; the `Release` workflow only builds.

## Data

- Never write migration code. A file that does not match the current format is ignored, or deleted and built again. No schema numbers, no legacy readers.

## YouTube

- One web view, made at launch, kept until quit. Never a second one, never recreated. The player page stays loaded and ready.
- A video starts: pause the song. A song starts: close the video window.

## Build and test

- Build: `./build.sh`. Last.fm: `LASTFM_KEY=... LASTFM_SECRET=... ./build.sh` (key from https://www.last.fm/api/account/create).
- Every change gets tests: new code and the code it touches. Every bug fix gets a regression test that fails without the fix. Code without tests gets them when it changes.
- Test: `swift test`. Test the release from Homebrew; a local build is only for debugging or profiling.
- Allocation tests: `swift test -c release --filter SpectrumCostTests` (unoptimized code allocates in every loop, so they run only in release).
- Sanitizers: `swift test --sanitize=address`, `swift test --sanitize=undefined`, `swift test --sanitize=thread`.
- Fuzzing: `docker run --rm -v "$PWD":/src:ro -v /tmp/fuzz:/out -e OUT=/out --shm-size=256m swift:latest sh /src/Fuzz/fuzz.sh 300`. Targets in `Fuzz/Targets`, seeds in `Fuzz/Seeds`, crashes in `/tmp/fuzz/crashes`. Do not edit sources while it builds.
- The fuzzed parsers must use only Foundation, so they compile on Linux.
- Every fuzzer crash becomes a regression test with a file in `Tests/OverdriveTests/Fixtures`.
- Uninstall: `brew uninstall --zap --cask overdrive`. The `.lyrics` and `.cache.lyrics` files in the music folders stay.

## Music library

- The library is read-only. The app never writes, moves, renames, or deletes an audio file.
- In a music folder the app writes only: `Cache.sqlite` (and its `-wal` and `-shm`) and `Loudness.plist` at the folder root, `.lyrics` files (lyrics the user keeps, LRC text) and `.cache.lyrics` files (the lyrics cache) next to the songs, with the name of the song (`Lyrics.kept`, `Lyrics.cached`). The app never reads or writes `.lrc` files, and, at the root of the first folder, `Plays.plist` (how many times each song was played), `Likes.plist` and the `Playlists` folder. The watcher ignores them: a write there must never start a scan.

## Library cache

**Hard requirement:** the filesystem, the cache, and the full-text index (FTS5, `bm25`) stay in strict sync, always and without exception.

- The cache and the index change only in one transaction (the triggers). `LibraryCacheTests` runs the FTS5 `integrity-check` after every scan step.
- The scan commits each step atomically, then shows it. The UI never shows a state the cache does not have. A replaced scan keeps what it committed. Only the first snapshot can show files that changed while the app was closed.
- Image files in the music folders (the extensions ImageIO reads, `Library.images`) also start a scan, so a new cover image shows (`cover image changed`).
- A scan starts on: FSEvents changes to files that the player plays (`Library.playable`: the extensions of `AVURLAsset.audiovisualContentTypes` that conform to audio, the same `Library.types` that the scan reads), folders that are removed or renamed (`kFSEventStreamEventFlagItemIsDir`, a moved album folder sends only its own event), volume mount and unmount, folder changes, and the launch. Every other file never starts a scan: covers, text, `.plist`s, `.lyrics`, `.cache.lyrics`, `.lrc`, `.DS_Store`, cache files, and hidden paths. The exception is a deleted `Cache.sqlite`, which starts a rebuild.
- Lost events: when FSEvents drops events (`MustScanSubDirs`, `UserDropped`, `KernelDropped`) or the watched root moves (`RootChanged`, `kFSEventStreamCreateFlagWatchRoot`), a scan starts (`Library.lost`).
- Sync: the app keeps in memory the date and size of every song as the cache has them (`Library.stamps`, read from SQLite after every scan and rebuild, so memory is never a second source of truth). Every 10 minutes (`Library.period`) it only compares the disk with them (`Library.changed`: a stat of each playable file, no reads, no SQLite writes, no redraw) and stops at the first new, changed, or gone song or walk error; then a normal scan updates SQLite. With no stamps yet, or other folders, it scans. The check is skipped when a scan ran in that time, a scan runs now, Low Power Mode is on, or the thermal state is serious or worse (`Library.sync`, the app only). Every hour (`Library.full` ticks) a full scan runs even when the quick check sees nothing (`sync full scan`), as the fallback of the watcher for the UI and the cache. File > Sync Library (Command-R) scans at once. A scan after the first one for the same folders skips the cached snapshot (`load(cached: false)`) and, when it finds no change, does not redraw the library (`scan unchanged`).
- `LibraryHarnessTests` runs a live `Library` with the watcher on a temporary folder; the harness never touches `UserDefaults`.
- Scope of the data files: a file that a folder needs to be readable again goes inside that folder, and a file that describes the collection goes at the root of the first folder. There is no "library" file, because the library has no file of its own: `Library.folders` is a `[URL]` in `UserDefaults` under the key `folders`, and its folders can sit on different volumes, so the library has no single root. Per folder: `Cache.sqlite` and `Loudness.plist`, both with paths relative to that folder (realpath). At the root of the first folder: `Likes.plist`, `Playlists/`, `Plays.plist`. Living inside the folder is what makes a moved folder keep its data: you move `/Music` to `/Back/Music`, add it again, and its tags, covers, and loudness come back from the file that moved with it, with no audio file read again. One file for the whole library cannot do this for a folder that is not the first one, because that folder's songs are keyed by a path under the old root. A one-folder library, the common case, is the same thing either way: the first folder is the only folder.
- `Loudness.plist` (EBU R128 loudness per song) lives at the root of each music folder, with paths relative to the folder (realpath), so a moved folder keeps its measurements.
- `Plays.plist` (how many times each song was played, `Plays`) lives at the root of the first music folder. Its keys hold no path: `file name` + U+001F + `album` + U+001F + `artist` (`Plays.key`), so the folder can move and a tag edit of album or artist starts the count again. The player counts a song once per full play (`Player.finished` calls `Plays.bump`). The count is in memory at once and shows in every list; the disk gets one atomic snapshot of every count (`Plays.flush`) at the hourly full scan, at quit, and before a folder change. A folder change that cannot write keeps the plays in memory and carries them to the new folder (`Plays.rebind`), so a moved folder loses nothing. Nothing writes while the folder is missing, like `Likes` and `Playlists`.
- Accepted limits of the play count. Each one is a choice, not a bug, and none of them needs a fix:
  - Editing the album or the artist tag of a song starts its count at zero. The key is the song as the tags name it, and that is what makes the count survive a moved folder.
  - Two copies of the same song (same file name, album, and artist) in different folders share one count, and `Library.neverPlayed` counts distinct keys, not files, so two identical copies make the never-played pool one song smaller.
  - Moving or deleting the first folder takes the counts of every folder with it. The file lives there, and the library has no root of its own.
  - Counts of songs in a folder that left the library stay in the file, unreachable. No prune: the keys hold no path, so nothing says which folder they belonged to.
  - A crash loses the plays since the last sync, at most one hour. The count is in memory at once; only the snapshot goes to the disk, so a play never waits for the disk.
- SQLite is only a cache, rebuilt from the music files. Each folder has its own `Cache.sqlite` at its root, paths relative to the folder (realpath). It is the only data that is not a binary plist.
- Tables: `tracks` (unique `path`, tags, `modified`, `size`, nullable `hash`), `tracks_album`, `covers` (JPEG), and the FTS5 `search` (`tokenize = 'trigram remove_diacritics 1'`), kept in sync by the insert, delete, and update triggers. Upserts use `ON CONFLICT(path) DO UPDATE`.
- Settings: `page_size = 65536` (before WAL), `mmap_size = 1 GiB`, WAL, `synchronous = FULL`, `fullfsync`, `checkpoint_fullfsync`, infinite `busy_timeout`. No version: to change the schema, delete the `Cache.sqlite` files.
- File > Rebuild Library Cache (`Library.rebuild`) reads every song again, ignoring the cached tags, and replaces each folder cache in one transaction: `DELETE FROM covers`, `DELETE FROM tracks`, every row and cover, `COMMIT` (`Cache.save(replacing: true)`), or `ROLLBACK` and the old cache stays. The triggers rebuild the search index in the same transaction. The UI keeps the old library until the commit, then shows the new one at once (no progress steps). A folder that cannot be walked, or without a cache, stops the rebuild before any write. Each folder is atomic on its own; several folders are separate transactions. It runs in the scan queue, one at a time with the scans.
- A folder that cannot be walked (no enumerator, or a directory error during the walk) keeps all its cached songs: nothing leaves the cache for that folder in that scan, and `library`, `folder unreadable` logs the errors.
- A failed cache write never shows: when a save returns false, the songs of that batch go back to their committed state (or stay out), and a failed removal keeps the songs. A replaced or failed scan or rebuild resets `shownFolders`, so the next scan shows what was committed. When a `Cache.sqlite` is missing at the start of a scan, the search connections close (`readers`), and `Cache.init` removes a leftover `-wal` and `-shm` before it opens a new file. `Library.add` compares real paths and skips a folder inside another one, also inside the same add.
- Album ids come from where the song is now (`Track.albumID`: the home-relative folder of the file and the album name), never from the stored column. When a folder moves, the scan writes the new ids back to the cache (`album ids moved`), so covers and albums stay whole without a rebuild.
- Covers are stored under `album id` + U+001F + a fingerprint of the album (`Library.coverKey`, `Library.fingerprint`: FNV-1a of the path, date, and size of each song, and of the name, date, and size of each image in the album folders). A cover is made again when the fingerprint changes (new tags or art in a file, a new or changed cover image), also across launches; an album without cover keeps an empty record, so it is not read again; the scan drops every stored cover that is not current (`dropping`, in the same transaction). Old records without a fingerprint are made again once. `Artwork` drops the image in memory when the cover bytes change. The `covers` process runs only in the app bundle. Logs: `reread` (reason: new, size, content by hash, date only), `covers to make` (new, changed), `covers saved`. `Library.edits` grows when a song keeps its path but its tags change (`Track.same`, a full compare; `Track ==` compares only the URL) or a cover changes. Screens that show tags or covers carry it in their identity (the Songs table, pushed screens, Up Next, playlists, Liked Songs, the album grid, the album strip), so they redraw. After every scan the player takes the new tags of its queue (`Player.refresh`), with the cover and the Now Playing info, without a stop.
- A song that cannot be read stays out of the cache, and its date and size stay in memory (`Unreadable`), so the 10-minute sync does not scan for it again until the file changes.
- Covers: the `covers` child process sends one record per album as soon as it is ready (`Picture.record`: index, size, JPEG). If the process dies, the covers already sent stay, the rest runs again one at a time, and the first album that is still missing is the one that crashes the reader: it gets no cover and the others go on (`Picture.collect`).
- The scan walks by the real path. Same date and size: cached tags. New size: read again. Same size, new date: hash (SHA-256); the same hash keeps the tags. New files get no hash. Gone or unreadable files leave the cache.
- Scans run one at a time. Each scan writes its adds, changes, removes, and covers in one transaction (`BEGIN IMMEDIATE` to `COMMIT`, or `ROLLBACK`). A failed write keeps the last good state.
- The scan is progressive: first the cache, then the walk, then batches of 256 files. `Library.load` calls `progress` after each step and stops without a write when a newer scan replaces it. Adding a folder scans at once.
- Search: fuzzy matches; FTS matches (words of 3+ characters) come first, in `bm25` order. The results (Songs with a query) show the matched albums above the songs (`AlbumStrip`). A click on an album opens it; its Play button plays it from the first song, shuffle off, and opens it on that song. Few albums fill the width; many scroll (`AlbumStrip.width`).

## Atomic writes

- Durable means `F_FULLFSYNC`; on a disk that does not support it (some network volumes return `ENOTSUP`, `EINVAL`, or `ENOTTY`), `Persist.durable` falls back to `fsync`, so a library on a NAS can still save. A failed folder creation and a failed plist encode log their cause (`folder failed`, `encode failed`).
- Every write of app data is atomic and durable. Period. This applies to every current file and every future file, without exception: binary plists through `Persist` (`write`, `move`, `remove`), and the cache through SQLite transactions. Never write in place, never `Data.write` directly, never a partial state.
- Every data file is a binary plist. No JSON, no plain text. Exception: `Cache.sqlite`.
- Read data files only through `Persist.read`. A missing file is normal; a file that cannot be read or decoded logs an error (`persist`, `read failed` or `decode failed`) before the app replaces it.
- `Likes` and `Playlists` keep absolute paths in memory, decoded once on load. They encode relative paths only when they save, against the current first folder. They reload when the folders change.
- `Likes` and `Playlists` use the real path of the first folder (`Library.real`) as the base, like the cache. They never write while that folder is missing (a drive not mounted yet): no folder is created on the boot disk and the real file is not replaced. They reload after every scan, so a drive that mounts later brings them back. A new playlist name is not valid while a file with that name is on disk.
- Song paths in the data files in a music folder (`Likes.plist`, `Playlists/`, `Loudness.plist`) are relative to that folder, so the library can move. `Plays.plist` holds no path at all: its key is the file name with the album and the artist. In `~/Library/Application Support/Overdrive` they are home-relative (`~/…`) under the home directory, absolute outside it, computed at runtime.

## Logging

- Every log is a structured log through `swift-log` (`Logging`, pinned to an exact version). Use the loggers in `Log` (`Log.player`, `Log.library`, ...). The message is a short, fixed event name; every value goes in `metadata`. Never put values in the message. Never use `print`, `NSLog`, `os_log`, or `os.Logger` directly.
- Log everything that helps to debug: user actions, player state changes, navigation, keys (key code and flags only, never the typed characters), scans, cache and file writes, network requests and responses, errors with their cause. Never log a password, a session key, or an API secret.
- The handler (`Handler`) writes each record as one JSON line (`time` in UTC, `level`, `label`, `message`, `source`, `metadata`) to `~/Library/Logs/Overdrive/<UTC hour>.log` (`Sink`), and the same record to the unified log (subsystem `org.delduca.Overdrive`).
- A new file starts every hour. Files older than one day (24 files) are deleted. Log writes are asynchronous, the only file writes that are: `Sink.write` returns at once, and a serial background queue does one `write(2)` with `O_APPEND` and one `fsync` for each burst within 100 ms (at once for errors and crashes), so the order stays and the caller never waits. `Log.flush` waits for the queue (quit, crash). Each record is whole or absent: when a file opens, a torn last record (no final newline, after a power loss) is cut off (`Sink.repair`). A crash signal or an uncaught exception writes a last record.
- The player logs what AVFoundation reports: `play to end failed` (also moves to the next song), `stalled`, `item error log`, `time control` (playing, paused, waiting with the reason), `seek done` (with `finished`), and the default audio output device (`Output`, CoreAudio, `output device`). The main window logs `window` (key, close, minimize, restore, open from the Dock or the shortcut). URLs with possible tokens go to the log without query or fragment (`YouTube.redact`). The search text is logged on purpose (it is not a password field); typed keys log only their code.
- Every decision logs its outcome: a failure with its cause (`error`, or `warning` for one attempt of many), an ignored or superseded event at `debug` or `trace`. `LogCoverageTests.everyDecisionLogs` lists the events that must stay.
- Only the app bundle (`org.delduca.Overdrive`) writes the file. Tests never write it (`Log.sink` is nil); they read the records through `Log.tap`.
- `LogTests` runs the components and checks their records, and checks that every public action of `Player`, `YouTube`, and the navigation logs.
- The log files are the only app files that are not binary plists or `Cache.sqlite`.

The lyrics cache is one file per song, next to it, with the name of the song and the `.cache.lyrics` extension (`Lyrics.key`): the lyrics from LRCLIB and lyrics.ovh, non-empty only. A cache file is valid for one month after its last write (`Lyrics.validity`, the modification date). After that the old lyric shows at once and the app asks the internet in the background; a non-empty, different answer replaces the file (atomic, through `Persist`), starts a new month, and replaces the lyric on screen, unless the user has edited it or another song shows; an empty answer or a failure keeps the old file and the old lyric, and the next show tries again.

## Behavior

- Tables: a double-click and Enter do the same: they start the first selected row as shown (`Player.start`; on the song that plays it pauses or resumes). On Songs, a double-click or Enter plays the row and opens its album (`go(.playing(track))`). The search results are the Songs page. On a playlist and Liked Songs, the double-click and Enter only play the row; they never open an album. In an open album, playing a song stays on that album. `Navigation.played` holds this rule.
- Playing a song from a list or the Play button of the results opens its album on that song (`Tracker.target`). From a search, an album opened by a click selects every matched song and scrolls to the first; if none matched, it selects the current song.
- The app never moves the focus by itself, except to the search field at launch. Option-Space (Edit > Find Song) is a global shortcut (two keys only; it must not collide with the system, such as Control-Command-F for full screen, Command-Space, Control-Space; `HotKey`, Carbon `RegisterEventHotKey`, no Accessibility permission): from any app it activates Overdrive, shows the main window (opens it when closed), and focuses the search with its text selected. It is the only global shortcut. Keys post `Key` notifications; only the top screen (`\.active`, through `Keys`) reacts. There is no other shortcut to focus the search field. Letters and digits typed outside an editable text go to the search field (`Focus.typing`), and the field takes the focus through its `NSSearchField` (`Focus.field`); while the query has text, a space, punctuation, and Delete go there too (`Focus.types`). The selectable synced lyrics are not an editable text, the lyrics editor is. Command-A selects all songs or all albums of the top screen from any focus, also the search field and the sidebar; only the lyrics editor keeps it for its own text. Tab moves between the search field and the sidebar. The arrows move the sidebar when it has the focus; otherwise they move the list. Control-Return opens the context menu without moving the pointer. Escape, from any focus (also the lyrics editor), closes the video, then goes back (the search text stays), then leaves the lyrics editor, then clears the search (`escape`). Space, Delete, Left, and Right act only when the search field has no text; Up and Down always move the list.
- Sorting: every table with a header sorts (`Sort`, `Sortable`; Songs, Up Next, playlists, Liked Songs). Every column has a `value:` and every `Table` a `sortOrder: order($sort, ...)`. A click sorts up, the next down, the third goes back to the own order of the list (`Sort.next`). Strings sort in the Finder order (`localizedStandardCompare`), Time as a number; equal values keep their order. The sort is never saved: it is view state, and it resets when the list is no longer `\.active` (another page, a pushed screen) and at launch. Actions (play, remove, duplicate) use the row ids, so they reach the right song in any order. A drag reorders Up Next and a playlist only in their own order.
- Albums: every album list goes from the oldest to the newest year, then artist, then title; an album without a year goes last (`Library.chronological`). The search results and the artist filter use the same order. All the albums sort once per scan (`byYear`); a search sorts only the albums it finds.
- Efficiency: sorting and search run on every click and key, so they must stay fast. A sort runs only when the sort or the list changes (`Sorted` keeps the result between redraws). A new sort gives the `Table` a new identity (`.id(sort)`): a SwiftUI `Table` that diffs a new order of thousands of rows hangs the main thread at 100% CPU. The Songs table also changes identity when a scan adds or removes songs (`Library.members`). Songs and Up Next sort and build their rows only when a token changes (`Sorted.apply(_:token:_:)`: `Library.scans`, `Player.revision` and `index`). Views that redraw often never do O(library) work: the window subtitle is memoized (`Memo`), album and artist lookups use dictionaries built once per scan (`Library.album`, `Library.albums(by:)`), only `TimeBar` reads `player.position` in the bottom bar, the docked lyrics never read the disk while they draw (`Lyrics.hasLocalLyrics` is stored), and the hidden floating panel draws nothing. The lyrics follow a new selection 150 ms after it settles (`Selected.delay`).
- Writes and scans wait for a quiet moment: the session writes 1 s after the last change (`Player.save`; quit writes at once with `Player.write`), FSEvents and volume changes start one scan 1.5 s after the last event (`Library.request`), Loudness saves at most every 30 s while it measures, and the SQLite search connections open once per folder change. Log records list at most 20 paths with a `count`.
- About: the first row of the sidebar (`row`, the same style as the other rows) opens the About page (`Page.about`, `AboutView`). The page shows the app icon, the version, a GitHub button, and blue text links (Markdown in `Text`, `.tint(.blue)`) for issues, releases, and every credit. Only the GitHub button has an icon. The credits are the same links as the README Credits section (`AboutTests` checks it). Every link click logs `open link`. The GitHub mark is the official Octicons `mark-github-24` SVG (pinned to 19.39.0), kept as text in `About.github` and read by `NSImage` as a vector template image, so it takes the color of the theme. It has no songs, no lyrics, and no query.
- Update check: opening About asks the GitHub REST API for the latest release (`Update.check`, `GET /repos/skhaz/overdrive/releases/latest`, JSON only, decoded with `Decodable`, anonymous, ephemeral session, 10 s timeout). Next to the version a blue rotating `arrow.triangle.2.circlepath` symbol shows until it ends; then a green checkmark (latest), a blue link to the new release (newer, numeric compare of `tag_name`; drafts and prereleases never count), or nothing (rate limit, server down, offline, timeout, odd answer). A failure never shows an error and never changes the app; it only logs `update check unavailable`. A good answer is kept for one hour, so opening About again does not spend the anonymous rate limit; a failure is not kept. Leaving the page cancels the request.
- Menus: `TrackMenu`, `CopyMenu`, `FileMenu`, and `GoMenu` are the only definitions of the song actions. The visible list publishes its selection (`Selected`, only when `active`). Do not give a plain key to a menu bar item.
- History: `Navigation` (in `Navigation.swift`) owns the screen and the back and forward stacks. `open` and `show` push the old screen and clear forward. An album or artist opened from Liked Songs, a playlist, Up Next, or About opens on Albums or Artists (`Navigation.show`), so the sidebar marks the page that shows; on Albums, Artists, and Songs it stays on that page. `restore` puts back the saved path at launch, except on Liked Songs, playlists, and Up Next, where the page always opens on its list. `refresh` cuts paths at albums that are gone. Each page draws its root and its pushed screens itself, in one `ZStack`; only the top screen of the current page shows, gets hits, and is `\.active`. Never use `NavigationStack`, `NavigationLink`, or `navigationDestination`: in a `NavigationSplitView` detail SwiftUI links only one stack, so a push on one page went to another page. Hidden pages and screens stay alive. Each pushed screen carries `.id(route)`. The Songs table carries `.id(library.query)`: a SwiftUI `Table` that diffs from a few rows to the whole library hangs the main thread. SwiftUI has no API to read or set the scroll of a `Table` or a `List`. Back with no back history closes the top screen and keeps it in the forward history (`pop`); the Back button and the swipe use `canGoBack`. Every place keeps the query it had (`Place.query`): back and forward put it back without opening the results. The saved path at launch goes only to the saved page, and only while there is no history (`restore(_:on:)`). A playlist that is gone leaves the history and the current page (`prune`). A route is the same screen while its key is the same (`Route` equality by key), so a scan that changes an open album does not rebuild it. Hidden screens never react: Delete, right-clicks, and Control-Return act only on the top screen. Gestures and mouse buttons do nothing while a dialog shows. The history is not saved to disk.
- Search: a change to another page (sidebar, back, forward, a new or deleted playlist) clears the query; the page that the search opens, or that a click on an artist name opens, keeps it (`Navigation.searching`). Opening an album or artist from the results keeps it. Otherwise only Escape, Command-K, and the clear button clear it. Every change to a query with text opens the results (the Songs page) from any screen (`Navigation.searched`); going back shows the old screen. The exception is a click on an artist name, which opens Albums filtered by that artist (`Navigation.filter`).
- Spectrum: a bar of thin bars over the full width, above the playback controls (`SpectrumBar`), shows the song that plays. Settings > Playback > Show Spectrum (`Player.showsSpectrum`, `UserDefaults` key `spectrum`, on by default, `Spectrum.enabled`) turns it off: no view, so no timeline and no FFT, and no tap on any item, so the audio thread copies nothing (`Player.adjust` drops the mix when there is no gain and no spectrum). Switching it clears the ring (`Spectrum.clear`), so a spectrum that comes back starts from silence. Every item gets an audio mix with an `MTAudioProcessingTap` (`Spectrum.tap`, before the gain, so the volume does not change it) next to the gain (`Player.mix`). The tap only copies mono samples into a fixed ring (`Spectrum.write`, `withLockIfAvailable`, no allocation, never waits on the audio thread). The view does a 4096-point FFT (Accelerate) once per frame (`Analyzer`, buffers made once), log bands from 40 Hz to 16 kHz with +3 dB per octave, fast rise and slow fall. Paused or muted: the bars fall, then the timeline stops. The bars run only while the window appears active (`\.appearsActive`, `SpectrumBar.running`): in the background, without focus, hidden, or minimized, the timeline stops at once and the tap copies nothing (`Spectrum.listening`, an atomic flag); they come back when the window is active. At most 60 frames per second (`SpectrumBar.interval`). The audio thread and each frame never allocate (`SpectrumCostTests`, which count every `malloc` through `malloc_logger`); only a new width makes the bands again. `Spectrum.init` runs the write once on the main thread, so the first song does not allocate runtime metadata on the audio thread. Each tap holds the `Spectrum` until the item goes (`SpectrumTests.theTapReleasesTheSpectrum`).
- Volume: each song is measured once (EBU R128, -14 LUFS, maximum +12 dB). Shuffle off: album gain. Shuffle on: track gain.
- Last.fm: each batch is marked on the disk before it is sent. A scrobble leaves only when Last.fm accepts it. Code 5 keeps it; 6, 7, and 13 isolate it; 1 to 4 reject it.
- After the daily limit (code 5), the periodic retry waits until the next UTC day (`LastFM.resume`); a new scrobble still tries at once.
- YouTube: the app searches with the YouTube page itself, so it needs no API key.
- Lyrics toggle: the toolbar button (`quote.bubble`) and Option-Command-Y show and hide the lyrics (`Player.lyrics`, saved in `Session.plist`, shown by default). Hidden lyrics do nothing: no disk reads, no requests, no cache folder, no floating window (`Lyrics.enabled`). Hiding saves a pending edit first. Show Lyrics in a Floating Window shows them again.
- Lyrics: no status label, no confirmation dialog. There is no save button: edits save by themselves. Every edit goes to the disk at once, with no delay (`Keeper`): a serial queue writes the newest text (atomic and durable, through `Persist`) and skips the texts that a newer one replaced, so typing never waits for the disk and a crash loses at most the write in flight. The main state takes the result in order (`Lyrics.stored`, by id). Deleting all the text removes the `.lyrics` file. `Lyrics.flush` writes the pending text and waits for the queue: before every navigation (`Lyrics.settle`), when the app loses the focus (`didResignActive`), when the window closes, and on quit. When a write next to the song fails (read-only or missing volume), the text goes to `Drafts.plist` (song path to text) and the lyric stays modified; the next show of that song puts the draft back and writes it again; a good write removes the draft. A lyric is valid only when not nil and not empty. The `.lyrics` file next to the song is read first; when it exists, the app never consults the internet. An edit cancels the in-flight lookup; what the user types always wins. The lyrics show the one selected song of the top screen (`Selected`), else the current song. They load at once, also when no lyrics view shows. The docked view shows while there is a current song (paused too) or one selected song, on an album, Songs, the search results, Liked Songs, and playlists; it hides on the Albums grid, the Artists list, and an artist's albums (`Navigation.lyrics`). It shares one `HStack` with the split view, so it never covers content. Only the user opens and closes the floating window.
- Lyrics races: opening another song cancels the lookup in flight; a refresh flushes a pending edit first and drops its answer when another song shows (`Lyrics.source`, `Lyrics.refresher` can be replaced in tests). LRC offsets and times are finite only. When no line is current (a new song, a repeat, a song that does not play), the synced lyrics scroll to the top (`SyncedLyrics.Coordinator.center`). The floating panel and the video window cancel a pending hide or close when they show again.
- Discovery: Controls > Discovery (`die.face.5`) has two pickers, each with 1, 10, 20, and 100 songs (`Library.randomCounts`). `Songs (n)` picks from the whole library (`Library.random`); `Never Played (n)` picks only the songs with no play (`Library.unplayed`, over the stored `neverPlayed` count and the same reservoir walk). Both use reservoir sampling (`Player.picked`): one pass, no copy of the library, no O(n log n) sort, and they read `everything`, never the search results. The chosen songs replace Up Next and the first one plays at once (`Player.random` calls `play`, so no stop and no confirmation). Each picker shows its size and is disabled when it is empty, and each value is disabled when its pool is smaller than the value (`library.total < number`, `library.neverPlayed < number`); an empty library disables the whole menu. An empty pick logs and does nothing.
- Plays: every song carries the number of times it played (`Plays.count`, memory first). The Songs table, Up Next, the playlists, and Liked Songs have a sortable `Plays` column (`Column.plays`, a number like `Time`), and an open album shows the count next to the duration. `Plays.revision` joins the token of every sorted list and `Library.rows` puts the count in each `Row`, so a song that just finished moves when the list is sorted by plays. `Library.neverPlayed` is the size of the never-played pool, kept in step by `Plays.flipped` (the library ignores a flip for a song it does not have) and rebuilt in every `show`.
- Up Next: the queue (`Player.queue`) is the buffer of what plays and what follows, a playlist that is never saved as one. The Up Next page (sidebar, `Page.upNext`, key `up-next`, `UpNextView`) shows the song that plays and the songs after it; the played songs stay in `Player.queue` for Previous but do not show. Add to Up Next, the one insert action of the song menu (Command-Return), puts the songs at the end of the list, after the songs added before it (`Player.inserting`, marks in `Player.added`); there is no second action that inserts after the current song. A drag reorders the songs after the current one (`Player.move`); Delete and Remove from Up Next remove the selected songs (`Player.remove`), never the song that plays; a double-click or Enter plays the row (`Player.jump`). With shuffle off, the edit also changes the play order. The session keeps the queue for the next launch. Clear Up Next (toolbar of the Up Next page, Controls menu), or a remove of the current song with every next song, asks for a confirmation (`clearUpNext`), then stops the song and resets the player as at launch with no song: no items, no current song, not paused (`Player.clear`).
- Restore: the saved queue comes back from the first snapshot only when every saved song is there; otherwise it waits for the end of the scan, and while no saved song is found (a drive not mounted yet) it waits for a later scan (`Player.waits`, `Library.loaded(complete:)`). The current song is found by its saved position, so a repeated song restores at its own place (`Player.located`). Nothing writes `Session.plist` before the saved queue is back or the user plays something new (`Player.write`). The end of the queue resets the scrobble state (`stop`). Add to Up Next after the end of the list adds to it. Shuffle, repeat, and the end of the queue save the session.
- Shuffle keeps where each song came from (`Player.shuffled`, `origin`), so turning shuffle off goes back to the same copy of a repeated song (`Player.unshuffled`; after an edit of a shuffled queue, the same occurrence).
- Floating lyrics: `Lyrics.floating` moves the lyrics to a borderless, nonactivating `NSPanel` at level `.floating` (`LyricsPanel`), created once on the first undock, with the same `Lyrics` and `Player`. The close button only docks the lyrics back. The window button and a double-click on the song dock the lyrics back, activate the app, and show the main window (`openWindow(id: "main")`). While `floating` is true, the docked view leaves.

## Deploy

1. Commit the change and push it to `main`.
2. Push a new tag, the last tag plus one.
3. Wait for the `Release` action (build only): `gh run watch <run-id> --exit-status`. If it fails, stop and report the failure.
4. Update this host:
   1. Stop the app: `pkill -x Overdrive`.
   2. Upgrade the app: `brew update && brew upgrade --cask overdrive`.
   3. Start it: `open -a Overdrive`.
   4. Check the version: `defaults read /Applications/Overdrive.app/Contents/Info.plist CFBundleShortVersionString`.
